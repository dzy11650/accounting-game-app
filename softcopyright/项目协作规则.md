# 会计小当家 · 项目协作规则（打包副本）

> 本文件与项目根目录 `PROJECT_RULES.md` 内容一致，随软著材料一并交付。
> 日常开发请以根目录版本为准。

---

## 0. 总原则

本项目经历过"乱码 commit、curl 上传失败、README 漏写版本"等踩坑。
所有涉及发版、提交、上传、文档的操作，必须先看本规则，避免重复犯错。

---

## 1. 编码与乱码（最高优先级）

### 1.1 提交信息
- 优先用英文写 commit message，避免编码往返损坏。
- 必须写中文时确保 UTF-8；提交后立即在 Gitee 网页核对，发现乱码立即重写并 force-push 修复。

### 1.2 文件与脚本
- 所有文本文件 UTF-8（无 BOM）。
- 不用 PowerShell 直接读写含中文文件，改用 Node.js 脚本。

### 1.3 上传产物到 Gitee Release
- 禁止 `curl -F file=@...`（Gitee 不接受，返回 200 但无附件）。
- 用 Node.js https + multipart 上传。
- **上传端点必须用 `attach_files`，不是 `assets`/`attachments`**：
  - 正确：`POST /api/v5/repos/{owner}/{repo}/releases/{release_id}/attach_files?access_token=...`
  - 错误：`.../releases/{id}/assets` → 404；`.../releases/assets` → 405（曾误判 Gitee 下线，其实 API 没变）。
- 上传前用 `DELETE .../releases/{release_id}/attach_files/{asset_id}` 清理旧包，避免残留非最新产物。
- README 中文文件名链接必须 URL 转义。

## 2. 版本迭代必须更新 README（硬性要求）

- [ ] 下载表更新到当前版本，链接 URL 转义且可点开。
- [ ] 新增"更新内容"章节。
- [ ] 补全历史版本（如 v2.0.2/v2.0.3）更新内容，不得遗漏。
- [ ] 软著登记号下证后标注。

---

## 3. 发版标准流程

1. 打包各端产物（Electron / NSIS / Tauri exe / APK）。
2. Node 脚本上传 Gitee Release（tag = 版本号）。
3. 更新 README（下载表 + 更新内容 + 历史补全）。
4. git commit（英文 message）+ push。
5. 网页核对：message 无乱码、附件齐全、链接有效。

---

## 4. 软著迭代规则

| 情况 | 例子 | 是否重登 | 动作 |
|------|------|----------|------|
| A. 小版本 | 修 bug、加课程、UI/性能优化 | 不需要 | 原软著有效，保留 git 记录 |
| B. 大版本/改名/重构 | 3.0、改名、核心重写 | 建议新登 | 新版本重新申请 |
| C. 换主体 | 个人转公司、转让 | 必须转让登记 | 合同 + 转让登记 |

## 6. 踩坑历史

- 中文 commit 乱码 → 改用英文。
- PowerShell 中文 GBK 损坏 → 改用 Node。
- curl -F 上传无附件 → 改用 Node multipart。
- 误用 `/assets` 路径（404/405）误判 Gitee 下线 → 正确端点是 `/attach_files`，API 未变动。
- Release 残留旧附件 → 上传前先 DELETE 清理旧包。
- 发版漏写 README → 发版必更新并补全。
